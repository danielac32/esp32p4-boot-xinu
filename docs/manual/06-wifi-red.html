Capítulo VI — WiFi y pila de red

Objetivo. Explicar cómo el ESP32-P4 se conecta a WiFi usando el ESP32-C6 como coprocesador de red (SDIO/esp_hosted) y cómo funciona la pila nativa de Xinu (ARP/IPv4/ICMP/UDP/TCP/DHCP) sobre ETH0 (espeth). Incluye código/flujo, uso y quién llama a cada parte.

2. Transporte WiFi: ESP-Hosted sobre SDIO (ESP32-C6)

2.1 Medio físico y concurrencia

El C6 está en el slot 1 del SDMMC compartido con la microSD (slot 0). Toda transacción del bus toma sdmmcBusLock() (monitor reentrante, system/sdmmcbus.c). Consecuencia: tráfico WiFi y lecturas FAT compiten en latencia/caudal.

2.2 RPC y datos (código/flujo)

  • Control (RPC TLV/protobuf): peticiones y respuestas sobre SDIO. Respuesta típica id_respuesta = id_peticion + 256. Funciones usadas: versión, init WiFi (requerido antes de otras RPC; evita 0x3001), MAC, modo STA, config, conectar/desconectar, escaneo (iniciar, nº de registros, fetch de registro i con bssid/ssid/canal/RSSI), señal del AP asociado (RPC 294, medido en placa), eventos (estado STA/scan/config). Ids concretos aparecen en xsh_wifi/xsh_wifi_scan.c y la capa wifinet.
  • Attach (wifi up): serializado por semáforo (un solo C6; attach concurrente corrompe s_ctx, medido). Escalera de configs (default/pullups/safe-1bit, ref. SDK). Tras adjuntar, sondea tramas y procesa el handshake PRIV (capacidades del host) — sin él el C6 ignora RPCs.
  • Datos (tramas): espethRead entrega una trama Ethernet cruda (sin cabecera hosted, retirada por transporte); espethWrite envía una trama. RX por sondeo/bombeo según integración.
  • Carrera RPC vs recepción (corregida): la hebra de red podía consumir respuestas RPC; se protege el camino RPC (disable/restore en tramo crítico + sdmmcBusLock + anillo/raw-RPC en control) para que wifi signal/scan funcionen con la pila activa.

Debug: ESP_HOSTED_CTRL_DEBUG/ESP_HOSTED_SDIO_DEBUG en platformVars (apagados por defecto: ruidosos con TCP). Quién llama: xsh_wifi, netboot, y la API exportada wifinet (usada por settings).

3. Dispositivo espeth (ETH0)

device/espeth-esp32p4/espeth*.c: Init/Open/Close/Read/Write/Control. Abstrae el C6 como interfaz Ethernet para la pila nativa. Control expone enlace/MAC/estadísticas (rx/tx/drops) según integración. Instancia ETH0 (esperada por DHCP/pila en [ETH0, ETH0+NETHER)).

5. Puesta en marcha y diagnóstico

Automática: netboot orquesta WiFi + asociación (credenciales/fichero, p. ej. /wifi.txt leído por el flujo) + DHCP + servicios. Con AP inexistente los reintentos pueden demorar; con AP correcta, decenas de segundos (medido). Manual: wifi up → wifi scan/join (o wifi connect según subcomando) → dhcpc ETH0 → ifconfig/ping/dns. Desde apps: API wifinet exportada (escanear, asociar, estado) — usada por settings.

6. Patrón de servidor TCP (referencia, usado por httpd/telnetd)

dev=getdev("TCPx"); tcpInit(); tcpRegister(dev);
tid=tcpAlloc(port,REMOTEPORT,1,TCPSM_NONE,NULL,NULL,dev); tcpAllocPassive(tid);
open(dev,TCP_PASSIVE); tcpOpen(dev);
control(dev,TCP_CTRL_RCVTIMEO,ms,0); /* evitar bloqueo eterno */
/* readline para cabeceras HTTP (\r\n\r\n); hebra releaser para PCB de escucha */

Servir desde SD toma sdmmcBusLock → impacta WiFi. Buffers grandes static si conviene (una petición a la vez, pila limitada).

7. Limitaciones conocidas

  • esp_hosted bare-metal aquí no expone monitor/sniffer, deauth, inyección ni power-save fino del C6 (afecta latencia en reposo). Prácticas: scan/ping/ARP en la red propia.
  • Recursos finitos (NUDP/NTCP, pool de paquetes); contención con DHCP/udpserver en escenarios concretos.
  • Contención SDMMC (slot 0 vs 1). P4_TIMER_FREQ desajustado (~9/8) afecta timeouts/delays.
  • httpd: PUT con disciplina de no-truncado (remove antes). udpserver apply bloqueado sin bootloader desde SD.
